# 사이클 02 준비 — 내 보드에서 실제 보드 화면으로

2026-10-12 준비안. 구현을 시작한 문서가 아니다. [사이클 01](cycle-01.md) 다음 작업이다.

## 이번에 사용자가 할 수 있게 만들 일

내 보드 목록에서 보드를 누르면 해당 보드의 **할 일 / 하는 중 / 완료** 컬럼과 카드가 보인다.
빈 보드에는 빈 상태를 보여주고, 접근 권한이 없는 보드 내용은 노출하지 않는다.
카드 생성·이동은 다음 구현 단위로 분리한다. 읽기와 접근 권한부터 검증한다.

## 역할별 작업과 순서

| 순서 | 담당 | 해야 할 일 | 확인할 결과 |

| 5 | 조율 | 코드·QA·학습 문서 검토와 통합 | main/push는 해당 단계의 사용자 지시에 따라 진행 |

## 구현 전 확인할 경계

- API 필드와 반환 구조는 기존 OpenAPI를 따른다. 문서와 코드가 충돌하면 먼저 근거를 확인한다.
- 카드 목록의 동일 position에 대한 정렬 기준, cursor 경계와 필터 조합은 기존 계약에 충분한 근거가 있는지 확인한다.
  근거가 없으면 임의 정책을 넣지 않고 사용자 결정이 필요한 항목으로 보고한다.
- `blocked`와 `warnings`는 DB에 새로 저장하지 않고 기존 계약대로 계산한다.
- 초대를 받았지만 아직 멤버가 아닌 사용자의 보드 상세는 기존 QA002 기준을 따른다.
- Figma 보드 상세 프레임을 조회한다. 호출 한도가 계속 막히면 기존 임시 UI 승인 범위가 새 화면에도 적용되는지 확인한다.
- 기존 개발용 DB와 fixture는 보존한다. 실제 검증은 별도 테스트 데이터로 수행한다.

## 이번 사이클의 종료 기준

1. 로그인한 사용자가 내 보드를 눌러 상세의 컬럼과 카드 목록을 볼 수 있다.
2. 빈 보드와 오류 상태가 구분되며, 비멤버에게 보드 내용이 노출되지 않는다.
3. 카드 정렬과 계산 필드를 실제 DB에서 검사하고, mock/HTTP/브라우저 증거를 나눠 기록한다.
4. 브라우저 클릭을 실행하지 못했다면 미검증으로 남긴다. 코드나 HTTP 검사로 대신 통과 처리하지 않는다.
5. QA 결과와 학습 문서를 남기고, 검증 서버 종료 여부를 인계한다.

## 그 다음 구현 단위

카드 생성 → 이동과 WIP 제한 → 카드 상세·수정 순으로 나눌 수 있다.
이번 준비안은 카드 생성·이동, 초대함·검색·알림까지 한꺼번에 구현하는 배정이 아니다.

사용자 요청으로 API·Next 프론트와 격리 PostgreSQL을 종료했다.
