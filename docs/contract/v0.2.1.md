# Taskify 계약 보완 v0.2.1

상태: v0.2 유지. 개발 전 보완. 재설계 아님.
기계 계약: taskify-openapi-v0.2.yaml 의 info.version 은 0.2.1.

## 이번에 닫은 것

1. OpenAPI 성공 응답 30곳에 description을 넣었다. $ref 오류 응답은 컴포넌트 description을 그대로 쓴다.
2. GET /boards 항목은 BoardListItem이다. Board에 myRole을 더한다. 저장 컬럼이 아니라 호출자의 BoardMember.role이다.
3. 버전 충돌과 도메인 충돌이 같은 409에 섞이던 쓰기는 examples로 코드를 갈랐다.
4. 아래 DB 제약과 트랜잭션은 v0.2 결정을 최종 확인한 것이다. 엔티티는 추가하지 않았다.

## 사용자 승인: 사이클 03 카드 생성·이동 (2026-10-13)

사용자가 다음 세 정책과 생성·이동 임시 UI 후 Figma 보정을 모두 승인했다.

- 생성은 POST /columns/{columnId}/cards, 컬럼 맨 끝에 추가한다. 이동은 POST /cards/{cardId}/move이며 beforeCardId 앞 또는 생략/null일 때 끝에 둔다.
- 목적지 순서 번호의 간격 소진 또는 Int32 범위 초과 시 목적지 컬럼을 1024 간격으로 다시 정리한다. 위치가 바뀐 기존 카드는 version도 증가한다.
- 같은 컬럼 순서 이동도 허용한다. WIP 계산은 이동 카드 자신을 제외한다. 자기 자신 앞 이동은 422 INVALID_INPUT이다. 결과 순서가 그대로면 성공하며 version과 활동 기록은 변경하지 않는다.
- 인증 후 시작 자원이 없거나 접근 불가하면 403으로 처리한다. 멤버가 아니면 NOT_MEMBER, Viewer는 FORBIDDEN이다. 권한 확인 뒤 잘못된 목적지·담당자·선행·삽입 기준은 422다. 다른 보드 연결은 CROSS_BOARD, 형식·삽입 기준 오류는 INVALID_INPUT이다.
- 새 tagNames는 보드 태그를 자동 생성한다. 대소문자만 다른 기존 태그는 재사용하며 기존 표기를 유지한다. 같은 요청의 중복은 하나로 묶고 공백을 임의로 제거하지 않는다.
- 기존 Owner/Editor 쓰기 권한, 목적지 컬럼 잠금 후 WIP 검사, 이동 If-Match(없음 428/충돌 409), 계산형 blocked/warnings를 유지한다. 카드·태그 연결·활동 기록은 원자적으로 저장한다.

## 보드 목록

### 사용자 승인: 사이클 02 보드 조회 정책 (2026-10-12)

사용자가 조율자의 조회 정책 제안 전체를 승인했다. 이 승인 기록과 OpenAPI 보완은
조율자의 명시 배정에 따라 BE가 기록하며 기존 역할 권한의 이번 배치 예외다.

- 오늘 범위는 GET 보드 상세/컬럼/카드 목록과 조회 권한이다. 신규 생성/이동 API는 제외한다.
- 컬럼과 보드 전체 카드 목록은 position ASC, 동률 id ASC다. 컬럼별 position 중복도 같은 전역 순서를 따른다.
- 카드 cursor는 position/id 경계와 boardId 및 columnId/assigneeId/tag 필터를 함께 담는다.
  같은 보드/필터에서 저장 경계 뒤를 조회하며 anchor 삭제 후에도 계속한다. 손상되거나
  보드/필터가 다른 cursor는 422 INVALID_INPUT이다. snapshot 일관성은 보장하지 않는다.
- 카드 필터는 AND이고 tag는 이름 정확 일치다. 형식이 유효한 다른 보드 또는 없는
  columnId/assigneeId 조건은 빈 목록이다. 태그 대소문자를 바꾸거나 공백을 제거하지 않는다.
- 존재하지 않는 보드와 비멤버(미수락 초대 포함)는 모두 403 NOT_MEMBER다.
  Owner/Editor/Viewer는 멤버인 보드의 모든 이번 조회에 접근할 수 있다.
- blocked는 직접 선행 카드가 있고 그 선행 카드의 컬럼이 완료가 아닐 때 true다.
  warnings는 blocked이면서 현재 카드 컬럼도 완료일 때만 [BLOCKED_BY_PREDECESSOR], 그 외 []다.
  두 값은 조회 계산이며 저장하지 않는다.
- 세 조회의 무효 세션은 401 UNAUTHENTICATED, UUID/query 형식 위반은 422 INVALID_INPUT이다.
  scalar query의 반복 배열은 string/UUID/integer 형식에 맞지 않아 422다. tag 빈 문자열은
  string 그대로 정확 일치 조건이며 새 minLength 제한을 추가하지 않는다. 알 수 없는 query
  key를 별도 거부하는 정책은 추가하지 않는다.

GET /boards 의 items[]는 id, title, description, color, version, createdAt, updatedAt, myRole이다. myRole은 OWNER | EDITOR | VIEWER. 멤버가 아닌 보드는 목록에 없다. 상세 GET /boards/{id}는 myRole을 넣지 않아도 된다. 멤버 목록으로 알 수 있다. 목록만 사이드바 배지에 필요하다.

### 사용자 승인: 보드 기본값 및 페이지 정책 (2026-10-11)

사용자 승인 원문: “좋아 네가 제안대로 색을 안 고르면 보라색, 최근 참여한 보드부터 표시, 잘못된 페이지 책갈피는 오류로 알려주기 승인한다.”

- 보드 생성 요청에서 color를 생략하면 #5534DA를 사용한다. 명시한 color는 기존 string 계약대로 사용하며 색상 선택 범위를 추가로 제한하지 않는다.
- 내 보드 목록은 호출자 멤버십의 joined_at DESC, 동률은 board_id DESC로 정렬한다.

- 삭제된 페이지 anchor와 페이지 사이 데이터 변경 처리의 세부 동작은 이번 승인으로 추가 확정하지 않는다.

인증 토큰 수명·세션·로그아웃 정책은 이 보드 승인에 포함되지 않는다.

## 버전과 오류

### 사용자 승인: 이메일 및 목록 페이지 경계 (2026-10-12)

- 이메일은 입력 그대로 저장·비교한다. 대소문자 변환이나 앞뒤 공백 제거를 하지 않는다.
  이메일 형식 검증은 기존 계약대로 유지한다. 형식에 맞지 않는 입력을 정규화로 허용하지 않는다.
- 내 보드 cursor는 마지막 항목의 참여 시각과 보드 ID를 담는다.
  해당 항목이 삭제돼도 저장된 정렬 경계 뒤의 목록을 계속 조회한다.
  페이지 사이 새로 참여한 보드는 목록 새로고침으로 확인한다.
  이는 snapshot 보장이 아니며 잘못된 cursor는 기존 승인대로 422 INVALID_INPUT이다.

### 사용자 승인: 브라우저 인증 B안 (2026-10-11)

사용자 승인 원문: “제안 b로 진행해줘”. Next.js 서버가 NestJS의 access/refresh를
보관하고 브라우저에는 불투명 세션 식별자 HttpOnly 쿠키만 전달한다.
NestJS의 Bearer와 JSON refresh 계약은 유지한다. Next.js는 브라우저용 인증/업무 중계 경로를 제공한다.
브라우저 새로고침·재시작 후에도 로그인 최초 시점의 7일 절대 만료 안에서 복구한다.

구현 규격: 쿠키 SameSite=Lax/Path=/, 운영 Secure, 서버 발급 랜덤 식별자를 사용한다.
변경 요청은 Origin이 설정된 웹 origin과 일치할 때만 허용하며 누락/불일치는 403 FORBIDDEN이다.
토큰은 브라우저 응답·브라우저 저장소·로그에 노출하지 않는다.
서버 저장은 PostgreSQL 기반으로 프로세스 재시작 후에도 유지한다.
세션 쿠키는 해시로 조회하고 BFF의 토큰 묶음은 환경 키에 의한 인증 암호화(AES-256-GCM)로 저장한다.
다중 요청/서버의 refresh는 같은 저장 행 잠금 아래 최신 토큰을 재조회하여 직렬화한다.

인증 DB의 refresh 해시는 검증/재사용 감지용이다. BFF는 upstream refresh에 필요한
토큰 원문을 복구해야 하므로 별도 web_sessions에 암호문으로 보관한다.
암호화 키 없는 실행 및 운영에서 메모리 저장 대체는 허용하지 않는다.
web_sessions와 인증 세션/회전 기록은 이 승인 동작의 저장 기반이며 신규 제품 기능이 아니다.
실제 DB/HTTP/브라우저 검증은 후속 단계로 분리하고 이번 기반 테스트로 통과를 주장하지 않는다.

### 사용자 승인: 인증 세션 정책 (2026-10-11)

사용자 승인 원문: “이대로 가자. 로그인 정책이 무난하고 일반적이다. 승인”.
직전 설명의 아래 제안을 승인한 것으로 기록한다.

- access 토큰 수명은 15분이다.
- refresh의 절대 만료는 로그인 시점부터 7일이다. 회전으로 만료를 연장하지 않는다.
- refresh 사용 성공 시 토큰을 회전하고 기존 토큰을 무효화한다.
- DB에는 refresh 토큰 원문 대신 해시를 저장한다.
- logout은 해당 access 토큰으로 식별하는 현재 로그인 세션만 폐기한다. 다른 로그인 세션은 유지한다.
- 모든 보호 요청에서 세션 유효성을 확인하여 logout 이후 기존 access 토큰의 접근도 즉시 거절한다.
- 회전으로 무효화된 refresh 토큰이 재사용되면 해당 로그인 세션을 폐기한다. 정상 사용자도 재로그인이 필요할 수 있다.
- 여기서 세션은 로그인 한 번으로 생성된 연결이다. 기기 전체 또는 사용자 전체 폐기를 뜻하지 않는다.

브라우저 토큰 보관 및 새로고침/브라우저 종료 후 유지, 비밀번호 변경 시 세션 처리,
이메일 동일성 정책은 이 승인에 포함되지 않는다. 세션 저장 모델과 원자적 회전·재사용 식별은
위 동작을 보장하도록 구현하고 실제 동시 refresh 검증과 구분해 보고한다.

versioned 쓰기에 If-Match가 없으면 428 IF_MATCH_REQUIRED. 서버 version과 다르면 409 VERSION_CONFLICT, details.version은 현재 값. 행은 바꾸지 않는다.

한 상태 코드에 코드가 둘이면 OpenAPI example로 구분한다.

- 멤버 role 변경 409: VERSION_CONFLICT 또는 LAST_OWNER. 보드 행을 잠근 뒤 owner 수를 센다.
- 컬럼 PATCH 409: VERSION_CONFLICT 또는 LAST_DONE_COLUMN.
- 컬럼 DELETE 409: COLUMN_NOT_EMPTY가 먼저, 그 다음 LAST_DONE_COLUMN.
- 카드 move 409: VERSION_CONFLICT 또는 WIP_LIMIT_EXCEEDED. 실패 시 column_id 불변.
- dependency 409: VERSION_CONFLICT 또는 DEPENDENCY_CYCLE. 보드 행 잠금 안에서만.

댓글 수정은 version 잠금 대상이 아니다. If-Match를 요구하지 않는다.

## DB 제약 최종

unique:

- users.email
- board_members (board_id, user_id)
- columns (id, board_id)
- cards (id, board_id)
- tags (id, board_id)
- tags (board_id, lower(name))
- invitations (board_id, invitee_email) where status = PENDING
- notifications (user_id, type, resource_id, due_at_snapshot) where type in (DUE_SOON, OVERDUE)

FK:

- cards (column_id, board_id) → columns (id, board_id)
- cards (predecessor_id, board_id) → cards (id, board_id). null이면 검사 안 함
- cards (board_id, assignee_id) → board_members (board_id, user_id). null이면 검사 안 함
- card_tags (card_id, board_id) → cards (id, board_id)
- card_tags (tag_id, board_id) → tags (id, board_id)

check: cards.predecessor_id <> cards.id. wip_limit는 null 또는 1 이상.

deferred trigger: 커밋 시 보드의 owner 수가 0이면 거절. 완료 컬럼 최소 1개는 앱 409 LAST_DONE_COLUMN으로 막고, trigger는 v1에서 owner에만 둔다.

position unique는 걸지 않는다.

## 트랜잭션 최종

- 보드 생성: board, owner member, 기본 컬럼 3. 세 번째만 is_done.
- 카드 생성·이동: 도착 column FOR UPDATE, count, WIP, position. 보드 행은 잠그지 않는다.
- 의존 설정·해제: board FOR UPDATE, 같은 보드 확인, 사슬 추적, predecessor_id, card.version.
- role 변경·멤버 삭제: board FOR UPDATE, owner 수, 0이면 LAST_OWNER.
- 초대 수락: invitation FOR UPDATE, PENDING일 때만 member insert. Owner를 만들지 않는다.
- 알림 job: INSERT ON CONFLICT DO NOTHING. 읽음은 키에 없다.

교차 보드를 앱이 먼저 보면 422 CROSS_BOARD. DB가 막은 것도 422로 번역한다.
